Key Findings

✅
No saturation at 100 VUs. p95 peaked at 17.7ms (internal) and 74.3ms (external) — both well under the 500ms gate. The FastAPI + async SQLAlchemy stack handled 100 concurrent VUs comfortably. Saturation point is above 100 VUs.
⚡
Internal baseline: ~10ms p95. No nginx, no TLS, no network hop. This is the raw FastAPI + Postgres floor. The stack is healthy and responsive at low VU counts.
🌐
nginx + TLS overhead: ~56ms. Run B p95 (74ms) minus Run A p95 (18ms) = ~56ms. This is home network RTT + TLS handshake. Both measurements have confounds (Run A adds OCI CPU pressure; Run B adds external network variability), so treat as directional.
⚠️
Transient spikes at 100 VU peak (~750–870s). Both runs show isolated p95 spikes of 112–395ms during the 100 VU hold stage. These recover fully within 30–60s and didn't trigger the error threshold. Likely momentary Postgres connection pool contention or ARQ worker competing for connections.
🔍
progress_write degrades last. Expected to be the first route to saturate (Postgres write locks), but it tracked at or below read routes throughout. Write contention is not a bottleneck at 100 VUs — Postgres pool headroom remains.
📈
Next ceiling step: push to 200–300 VUs. To find the true saturation point, increase peak VUs. Predicted first failure signal: Postgres connection pool exhaustion (watch pool wait time before 5xx errors appear).
